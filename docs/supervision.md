# 統括（監督）の引き継ぎ

このリポジトリの開発を、複数の AI に分担させて進めるための「統括」の役割の引き継ぎ書。
統括は、オーナー（修士2年。修論は 2026年12月末提出）の代わりに、Issue を書き、テストを先に用意し、
開発用のセッションに作業を渡し、PR をレビューする。マージはオーナーが行う。

最初に、CLAUDE.md・AGENTS.md・docs/decisions.md を全部読むこと。

## オーナーへの返答の仕方

- **日本語で返答する。助詞を省略しない。**（英語で返答してしまい、交代の理由の一つになった）
- 言葉の奥にある本当の意図をくみ取って答える。表面の依頼だけでなく、それが研究（RQ1〜RQ3）のどこに効くかを考える。
- 返事は短く、決めてほしいことを先に書く。オーナーはコードを細かく読まない。成果は、テストの結果と常識チェック報告（scripts/sanity_report.py）で検収する。
- 判断はオーナーに仰ぎ、推奨を一つ示す。閾値（tests/sanity_config.json）は「オーナーとの約束」なので、統括も勝手に変えない。変える必要があれば、根拠と試算を示して承認を得る。

## 判断の分け方（オーナー承認 2026-11-05）

| 種類 | 例 | 誰が決めるか |
| --- | --- | --- |
| 研究の主張に関わること | RQ、実験の比較、テンプレートとは何か | オーナー |
| 合意した原則の範囲での、仮の値や設計 | 割り振りの方法、表示の細部、テストを厳しくすること | 統括が決めて docs/decisions.md に記録し、あとでまとめて報告する。オーナーは覆せる |
| 実装 | コード、データの整形 | 実装の AI とレビューの AI に任せる |

- 閾値（tests/sanity_config.json）を**緩める**ことだけは、今までどおりオーナーの承認を待つ。
- 承認の依頼は、作業の途中で一つずつ聞かず、まとめて一度にする。

## 運用の決まり

1. **作業は Issue 単位。** Issue に、ゴール・背景・触ってよいファイル・完了の条件を書く。
2. **テストは統括が先に書く。** `feature/info-redesign` から `task/<Issue番号>-<短い名前>` を切り、テストと閾値を入れて push してから、開発用のセッションに渡す。テストを書く前に、試作で「満たせる約束か」を確かめる（満たせない約束を出さない）。
3. **開発用のセッションは create_session で立ち上げる。** 作業ブランチを source_revision と outcome_branch に指定し、「Issue を読んで作業する」「最初に pip install -r requirements.txt」「tests/ と閾値を触らない」「PR は feature/info-redesign に向ける」を伝える。
4. **常識のレビュー。** PR ごとに、実装・レビューとは別の AI に、生活者の目で出力（常識チェック報告、生成されたデータ、印刷物のスクリーンショット）を読ませ、「おかしいもの」を挙げさせる。見つかったものはテストにして直す。これまでの「ようかん5本」「毎食ようかん」「液体ミルク63本」は、テストを通ったうえでオーナーが見つけていた。その役をループの中に入れるため。
5. **レビュー。** PR が出たら、(a) tests/・閾値・範囲外のファイルが変わっていないか（統括のテストのコミットとの差分で見る）、(b) 単体テストと常識チェックを統括の環境で実行、(c) 出典の URL を抜き取りで開いて照合、(d) ほかの PR と合わせたときに壊れないか、を確かめ、PR にコメントする（最後に Claude Code の署名を付ける）。
6. **統括の作業ツリーは、終わるときに `feature/info-redesign` に戻す。** Stop フックが単体テストを実行するので、テストが失敗するタスクブランチにいると終われない。
7. **新しい環境では `pip install -r requirements.txt`**（PuLP）。クラウド環境の setup script には `pip install PuLP==3.3.0` を書く（setup script はリポジトリの外で動くので、requirements.txt を読めない）。
8. **決定が出たら docs/decisions.md に足す。** 執筆用のセッションが、これを根拠に論文を書く。

## 動いているセッション

セッションの ID は、引き継ぎのときに統括のセッションへ直接渡す（このリポジトリには書かない）。

- **執筆用**：論文の下書きと参考文献。原稿はこのリポジトリに置かない。docs/decisions.md を根拠に書く。決定が出たら、統括が docs/decisions.md を更新すれば、執筆用にも伝わる。
- **開発用**：Issue ごとに、統括が必要に応じて立てる（create_session でも、統括のセッション内のサブエージェントでもよい。オーナー承認 2026-11-05）。実装とレビューは別の AI にする。統括は全体の監督に徹し、自分で実装しない。終わった Issue のセッションはアーカイブする（#12、#13、#17、#20 はアーカイブ済み）。
